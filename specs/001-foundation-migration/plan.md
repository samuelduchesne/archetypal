# Implementation Plan: archetypal 3 foundation and migration from v2

**Branch**: `claude/admiring-meitner-1f43qk` (spec 001) | **Date**: 2026-11-22 |
**Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/001-foundation-migration/spec.md`

## Summary

Spec 001 delivers what a user gets when they install archetypal 3, and the project every other
v3 spec is built in.

**Foundation (first).**

1. **Generate.** The project is generated with `/project-kit:new-project` (Python, src
   layout, pyright, MkDocs, Keep a Changelog, Claude agent instructions) in a scratch folder,
   then carried onto a `v3` branch of this repository, which keeps its history and its own
   spec-kit files. `.cruft.json` links it to the template for later upgrades (research R1).
2. **Branch.** v2 moves to `v2.x`. v3 is integrated on `v3` and becomes `main` at milestone M1.
   Milestones are GitHub pre-releases; the template's publish job skips them, so nothing
   reaches PyPI before UP-3 (R2, roadmap C-18).
3. **Tool.** Shared tooling for every spec: strict pyright with unknown types as errors, ruff
   with docstrings, three test tiers with a two-minute unit budget, Linux, macOS and Windows
   (R3, R9).
4. **Instruct agents.** `CLAUDE.md` and every `tasks.md` require `/idfkit:developing-with-idfkit`
   before writing code that imports idfkit, and `/project-kit:diataxis` for every docs page
   (R4).
5. **Document.** A Diátaxis site whose sections appear with their first page, every page
   tagged with its kind and checked, every example run, reference generated from the code
   (R5).

**Surface and migration (after 002 and 003).**

- One public interface and one `archetypal` command (`reduce`, `merge`, `compare`,
  `translate`) over 002's and 003's functions, with v2's `reduce` form and default UMI output
  (R6).
- One table of removed v2 capabilities drives the import errors, the rejected options, the
  migration guide's table and its coverage check against the v2 package (R7).
- A tutorial to a first UMI library, a migration guide, and v2's lifecycle on `v2.x` (R11).

All decisions and their evidence are in [research.md](research.md).

## Technical Context

**Language/Version**: Python 3.10–3.12 (`requires-python = ">=3.10,<3.13"`, bounded by
epinterface; C-07, R9).

**Primary Dependencies**:
- epinterface, from the SBEM fork (C-17), through `[tool.uv.sources]`;
- idfkit `>=1.3,<2`, used through its typed interface (spec 002, R18);
- click `>=8.1,<9` for the command line (R6);
- pydantic v2 and numpy (spec 002).

**Storage**: files only: SBEM archetypes in epinterface's serialisation, reports as JSON
beside them, UMI libraries as UMI JSON (FR-012, FR-014).

**Testing**: pytest with tiers `unit` (default), `energyplus`, `reference`; pytest-timeout;
hypothesis; `pytest-markdown-docs` for documentation examples (R3, R5).

**Target Platform**: Linux, macOS and Windows; pure Python (FR-001, R9).

**Project Type**: Python library with a command line.

**Performance Goals**: the unit tier finishes in ≤ 120 s (R3). The command line adds no
measurable time to the functions it wraps.

**Constraints**:
- no PyPI release before UP-3; milestones are git tags (C-18, R2);
- no import-time side effects (FR-006, R10);
- nothing from v2 carried as is (C-04);
- generated files come from the template and are changed only by the edits R1 lists.

**Scale/Scope**: v2's public surface: 13 group options, 2 commands, 12 public modules and the
names they export (finding 5; the exact list is generated by R7's script).

No item is left as NEEDS CLARIFICATION. Research R1–R14 resolves every unknown. 003's
function names are an input from its plan (R14), not an unknown of this plan.
