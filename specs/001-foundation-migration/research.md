# Research: archetypal 3 foundation and migration from v2

**Plan**: [plan.md](plan.md) | **Spec**: [spec.md](spec.md) | **Date**: 2026-11-22

This file settles every open point in the plan's Technical Context. Each entry gives the
decision, why it was chosen and what else was considered.

Spec 001 owns the package as a whole, so the decisions here apply to every v3 spec. Spec
002's plan cites them instead of deciding them again (its research R15 and R16 point here).

Facts come from:

- the v2 tree on `main` (release 2.18.11, 2026-10-25);
- the project-kit-cookiecutter template at commit `73646700cea8`, generated in a scratch folder
  on 2026-11-22 with the answers of R1;
- the three skills the user named for this work: `/project-kit:new-project`,
  `/project-kit:diataxis` and `/idfkit:developing-with-idfkit`.

## Findings that shape the plan

1. **`/project-kit:new-project` creates a new folder, not a branch.** It refuses a destination
   that exists and is not empty. It runs `cruft create`, then `specify init --here --force`,
   then `git init` and a first commit. archetypal is an existing repository with a v2 history,
   its own `.specify/` (constitution 1.5.0, roadmap 1.11.0) and its specs. The generated tree
   must therefore be carried onto a branch of this repository, and the generated spec-kit and
   git folders must not replace the project's own (R1).
2. **The template's release workflow publishes to PyPI on every published GitHub release.**
   `on-release-main.yml` runs `uv publish`, then `mkdocs gh-deploy`. Roadmap C-18 forbids a
   PyPI release before UP-3, so the workflow must skip milestones (R2).
3. **The template targets more than archetypal can.** It writes `requires-python =
   ">=3.10,<4.0"`, classifiers up to 3.14 and a CI matrix of 3.10–3.14 on Ubuntu only. The
   spec needs 3.10–3.12 (FR-001, C-07), with Linux, macOS and Windows (FR-001, SC-001).
4. **v2's documentation is Sphinx on Read the Docs** (`.readthedocs.yml`, `docs/conf.py`, RST
   pages). The template's is MkDocs Material on GitHub Pages. The two sites can live side by
   side (R5).
5. **v2's command line** (`archetypal/cli.py`, click) has a group with 13 options (data, logs,
   images and cache folders; response caching; log file, console, level, name and file name;
   `--ep_version`; `--debug`) and two commands: `reduce` (`IDF...`, `-o/--output`,
   `-w/--weather`, `-p/--parallel`, `-z/--all_zones`, `-v/--version`) and `transition`
   (`IDF...`, `-v/--version`, `-p/--parallel`, `-y`). Every one must be either kept or
   rejected by name (FR-013).
6. **v2's runtime dependencies** include eppy, energy_pandas, esoreader, shapely, pyclipper,
   pypoly2tri, transforms3d (geomeppy's), matplotlib, scikit-learn, CoolProp, networkx,
   pycountry, requests, tqdm and sigfig. None is needed in v3 (SC-002).

## R1 — Generating the project with `/project-kit:new-project`

**Decision.** The v3 project is generated by `/project-kit:new-project` (Python), then carried
onto this repository's `v3` branch.

1. **Answers.** The maintainer runs the skill and gives these answers. The author's name and
   email come from the maintainer at run time; they are not recorded in this plan.

   | Question | Answer | Why |
   |---|---|---|
   | `project_name` | `archetypal` | The distribution keeps its name (C-08: `archetypal<3` pins v2). |
   | `project_description` | "Create, translate and codify building energy archetypes on SBEM." | The constitution's purpose. |
   | `author_github_handle` | `samuelduchesne` | Repository owner. |
   | `layout` | `src` | Published package; tests run against the installed package. |
   | `minimum_python_version` | `3.10` | C-07. |
   | `development_python_version` | `3.12` | The highest version epinterface allows. |
   | `type_checker` | `pyright` | Strict typing (constitution VI, SC-005). |
   | `include_py_typed`, `include_github_actions`, `codecov`, `deptry`, `mkdocs`, `changelog` | yes (defaults) | Typed public library, CI, coverage, dependency hygiene, Diátaxis site, Keep a Changelog. |
   | `publish_to_pypi` | yes | v3 goes to PyPI at C-18's publish point; R2 keeps the workflow from running before it. |
   | `dockerfile`, `devcontainer`, `dvc` | no | A library: nothing to deploy, no large data in git. |
   | `agent_instructions` | `claude` | The project is developed with Claude Code. |
   | `agent_profile` | `full` | Writes the fuller `CLAUDE.md` (testing, typing and changelog guidance), which R4 extends. |
   | `open_source_license` | MIT license | Unchanged from v2. |

2. **Where.** The skill generates `archetypal/` in a scratch parent folder (outside the
   repository), at template commit `73646700cea8` or later. The full commit is recorded in
   `.cruft.json`.
3. **Carrying it over.** On a new `v3` branch cut from `main`:
   - remove the v2 tree (`archetypal/`, `geomeppy/`, `docker/`, `Dockerfile`, `paper/`,
     `install_energyplus.sh`, `poetry.lock`, `tox.ini`, `.readthedocs.yml`, the Sphinx
     `docs/`, the old workflows). It stays on `v2.x` (R2);
   - copy every generated file except `.git/`, `.specify/` and `.claude/`. The repository
     keeps its own spec-kit files, specs, constitution and roadmap;
   - merge `CHANGELOG.md`: keep v2's history below the template's header (FR-026);
   - keep `LICENSE.md`'s copyright years and holder; the template's `LICENSE` replaces it if
     identical in substance;
   - delete the template's examples (`src/archetypal/foo.py`, `tests/test_foo.py`).
4. **Edits after generation**, each visible in the cruft diff (R3 lists the tooling ones):
   - `requires-python = ">=3.10,<3.13"`, classifiers 3.10–3.12, tox and CI matrices trimmed;
   - CI matrix extended to macOS and Windows (R9);
   - `on-release-main.yml` guarded (R2);
   - `CLAUDE.md` extended with the agent rules of R4.
5. **Later template updates** go through `/project-kit:upgrade-project`, which works because
   `.cruft.json` links the project to the template.

**Rationale.** The template is the user's standard; generating with the skill rather than by
hand records the template version and answers, so later upgrades are mechanical. Carrying the
generated tree onto a branch keeps the repository's history, issues and stars, which v2 users
and the `archetypal<3` pin rely on.

**Alternatives considered.**

- *Run `/project-kit:upgrade-project` on the v2 tree.* Rejected: it would link the template to
  a poetry project with a flat layout, then fight v2's files on every merge; v3 removes that
  tree anyway.
- *A new repository.* Rejected: it splits the project's history, issues and PyPI name from
  its repository.
- *Run the skill inside the repository.* Not possible: the destination must be empty, and
  `specify init --force` would overwrite the project's spec-kit files.

## R2 — Branches, milestones and releases

**Decision.**

- **`v2.x`** is cut from the `v2.18.11` release commit at the start. It receives v2 security
  fixes only (FR-020, C-08), keeps v2's poetry, Sphinx and Read the Docs setup, and releases
  `2.18.x` patches.
- **`v3`** is the integration branch for v3 work from the first task until milestone M1. CI
  runs on pushes to `v3` and on pull requests into it.
- **At M1** (001–003 verified, roadmap C-18), `v3` is merged into `main`, so `main` holds
  v3 and the milestone tag `v3.0.0a1` is on `main`. Until then `main` holds v2 unchanged.
- **Milestones** are GitHub *pre-releases* on tags `v3.0.0aN`. The template's
  `on-release-main.yml` is edited so that:
  - `publish` runs only when `github.event.release.prerelease` is false;
  - `deploy-docs` runs for every published release, pre-releases included, and no longer
    waits for `publish`.
- **The first PyPI release**, v3.0.0, is a normal GitHub release cut when UP-3 is met (C-18).
  Nothing else in the workflow changes for it.

**Rationale.** It meets C-18 with a two-line guard in the template's workflow rather than a
second workflow. Pre-releases make each milestone visible and installable
(`uv add "archetypal @ git+https://github.com/samuelduchesne/archetypal@v3.0.0a1"`), which
C-18 counts on for outside feedback.

**Alternatives considered.**

- *Plain tags, no GitHub release.* Rejected: milestones would not deploy the docs, and users
  would not see them.
- *Delete the publish job until UP-3.* Rejected: it diverges from the template until someone
  remembers to restore it; the guard is self-documenting and harmless after v3.0.

## R3 — Tooling shared by every v3 spec

**Decision.** These edits follow generation (R1, step 4) and apply to the whole package:

- **Ruff:** keep the template's rule set (YTT, S, DTZ, LOG, PIE, PT, RET, TC, PTH, B, A, C4,
  T10, SIM, I, C90, E, W, F, PGH, UP, RUF, TRY, PERF, FURB), `line-length = 120`, preview
  format, `future-annotations`. Add `D` (`convention = "google"`), `NPY`, and `PL` with
  `max-args = 8`. Per-file ignores for `tests/*`: `S101`, `D`, `PLR2004`.
- **Pyright:** the template's `strict`, plus `reportUnknownMemberType`,
  `reportUnknownVariableType` and `reportUnknownArgumentType` as errors, so no untyped object
  leaks in from a dependency (SC-005).
- **Dependencies:** runtime `epinterface>=X,<Y` resolved to the SBEM fork through
  `[tool.uv.sources]` (roadmap C-17), `idfkit>=1.3,<2`, `click>=8.1,<9` (R6),
  `pydantic>=2.9,<3`, `numpy>=1.26`. Development group: the template's, plus `pytest-timeout`,
  `hypothesis`, `pytest-markdown-docs` (R5), `mkdocs-click` (R6).
- **Tests:** three tiers selected by markers, as spec 002 needs them and as later specs will:

  | Tier | Marker | Runs | Budget |
  |---|---|---|---|
  | Unit | none | every push, every Python and OS of R9 | ≤ 120 s wall-clock; ≤ 5 s per test |
  | Integration | `energyplus` | every pull request, Linux, Python 3.12 | ≤ 10 min |
  | Reference | `reference` | weekly, manual, on milestone tags | none |

  `pytest-timeout` sets 5 s per unit test. A `pytest_sessionfinish` hook in `tests/conftest.py`
  fails the default selection when it exceeds 120 s. `--durations=15` is always on.
  `hypothesis` has a `ci` profile capped at 50 examples and a 500 ms deadline.
- **Documentation check:** the template's `check-docs` job (`mkdocs build -s`), plus the
  example and Diátaxis checks of R5.

**Rationale.** These are the standards of constitution VI made concrete once, so every spec
inherits them. The two-minute unit tier is the user's general rule; spec 002's research R16
gives its first application.

**Alternatives considered.** *Let each spec's plan set its own tooling.* Rejected: tooling is
shared, and a reduction plan is the wrong place to change a ruff rule.

## R4 — Instructions for agents

**Decision.** `CLAUDE.md` (generated by the template, R1) gets a section "Skills to load",
and every `tasks.md` of a v3 spec repeats the rule in its header:

- **Code that imports idfkit.** Before writing or changing any module or test that imports
  `idfkit`, the agent loads `/idfkit:developing-with-idfkit`. The skill locates the idfkit
  installed in the project's `.venv` (after `make install`) and loads the reference pages for
  that exact version, so code follows the API it will run against. The agent reads the
  smallest reference page that covers the task.
- **Documentation pages.** Every page under `docs/` is written or revised with
  `/project-kit:diataxis` (R5): name the mode first, read that mode's reference, brief the
  `project-kit:editor` agent with verified facts, run the mode's failure checklist, wire the
  nav.
- **Template upkeep.** Template updates go through `/project-kit:upgrade-project`; generated
  files are not re-created by hand.

**Rationale.** These are the user's instructions for how v3 is built. Writing them where
agents read them (`CLAUDE.md`, task headers) makes them apply to every session, not only to
those that remember this plan. The idfkit skill also complements spec 002's typed-interface
rule (002 research R18): it shows the typed API, and the checks enforce it.

## R5 — Documentation: authoring, structure, checks and hosting

**Decision.**

- **Authoring.** Pages are written with `/project-kit:diataxis` (R4). Following that skill:
  - no empty sections are scaffolded. A section's folder and nav entry appear with its first
    page. FR-022's four sections all exist at M1, because FR-023's minimum content puts a page
    in each;
  - titles show the mode: "How to …" for how-to guides, "About …" or a *why* question for
    explanation, the name of the thing in the code for reference, the result for a tutorial;
  - reference is generated: mkdocstrings for the Python API, `mkdocs-click` for the command
    line (R6), so it cannot drift (FR-023, US3 scenario 2).
- **Structure** (`mkdocs.yml`, Material, with `navigation.indexes`):

  | Section | Folder | Pages at M1 (FR-023, plus 002 and 003) |
  |---|---|---|
  | Tutorials | `docs/tutorials/` | "Your first UMI library": install from git, download the example model and its results, reduce, open the library |
  | How-to guides | `docs/how-to/` | "How to migrate from archetypal 2" (FR-017–FR-020); 002's reduce, merge and compare guides; 003's |
  | Reference | `docs/reference/` | Python API (mkdocstrings), command line (`mkdocs-click`), report files, removed names (generated from the table of R7) |
  | Explanation | `docs/explanation/` | "About archetypal: where it sits in the stack"; 002's "About reduction"; 003's |

  The home page `docs/index.md` is a short orientation (explanation). The changelog page is
  reference.
- **Diátaxis tag (SC-008).** Every page starts with front matter `diataxis: tutorial |
  how-to | reference | explanation`. A unit test reads every page under `docs/` and fails
  unless each has exactly one valid tag and sits in the folder of that kind (the home page
  excepted).
- **Examples run (FR-024, SC-004).** Python code blocks in pages are run by
  `pytest-markdown-docs` in a `docs-examples` job. Command-line blocks marked `console` are run
  by a small test that executes each `$ archetypal …` line in a temporary folder with the
  example files. The migration guide's "after" examples are ordinary Python blocks, so the
  same job runs them (FR-018).
- **Hosting.**
  - v3: GitHub Pages, deployed by the template's `mkdocs gh-deploy` on every published
    release and milestone (R2), so the site matches the latest tag (FR-024's "current
    release").
  - v2: stays on Read the Docs, built from `v2.x` with its Sphinx setup (FR-025). Read the
    Docs' default version is switched to `v2.x` at M1.
  - Each site links to the other: v3's home and migration guide link to v2's docs; v2's docs
    get a banner pointing to v3 in the final v2 release (FR-021, R11).

**Rationale.** It follows the skill the user named and the spec's guarantees: one kind per
page, generated reference, examples that run. Keeping v2 on Read the Docs needs no migration
of v2's RST and keeps every existing v2 link alive.

**Alternatives considered.**

- *Versioned docs with `mike` on GitHub Pages, v2 included.* Rejected: it means converting v2's
  Sphinx docs or building them in a second toolchain; Read the Docs already hosts them.
- *Zensical.* Not now: the template generates MkDocs Material and the diataxis skill supports
  both; switching later is a template upgrade.
- *`mktestdocs` for examples.* Rejected in favour of `pytest-markdown-docs`, which runs each
  block as a pytest test with fixtures and shows the page and line on failure.

## R6 — Command line

**Decision.**

- **Library:** click (`>=8.1,<9`). v2 used click, epinterface uses click, and `mkdocs-click`
  generates its reference. epinterface's exact pin (`click==8.1.7`) is loosened by UP-4 in the
  fork.
- **Module:** `src/archetypal/cli/`, entry point `archetypal = "archetypal.cli:main"`.
- **Commands** (contract: [contracts/cli.md](contracts/cli.md)):
  - `reduce MODELS... -w/--weather EPW -o/--output PATH` with `--to umi|sbem` (default
    `umi`, v2's result, scenario 1.4), `--results` (one SQLite file per model, optional),
    `--layout`, `--threshold`, `-p/--parallel N`, `--force`;
  - `merge`, `compare`, `translate` (UMI ↔ SBEM), thin wrappers over 002's and 003's functions.
- **Kept v2 options:** `-o/--output`, `-w/--weather`, `-p/--parallel`; and on the group,
  `--log-level` and `-d/--debug` (show tracebacks).
- **Rejected v2 options and commands (FR-013).** One table, `REMOVED_OPTIONS`, lists each
  with its replacement or reason. Each is declared as a hidden click option or command whose
  callback raises a usage error naming it, before any work. This covers `transition`,
  `--ep_version`, `reduce -v/--version` (as `--version` on `reduce`, distinct from the group's
  own `--version`), `-z/--all_zones`, `-c/--cache-responses`, `--data-folder`,
  `--logs-folder`, `--imgs-folder`, `--cache-folder`, `-l/--log-file`, `-s/--silent`,
  `--log-name` and `--log-filename`.
- **v2-style invocation** (scenario 1.4): `archetypal reduce a.idf b.idf -w w.epw -o lib.json`
  simulates each model once through idfkit (002's `simulate=True`), reduces it to the
  core/perimeter layout UMI needs, and writes one UMI library through 003's writer.
  Directories and glob patterns expand to `*.idf` and `*.epJSON` files, sorted.
- **Exit statuses (FR-014):** 0 success; 1 failure; 2 usage error (click's); 3 partial
  failure (some models failed, the output written without them and the failure listed);
  4 success with losses reported. A library is never written with a failed model silently
  missing: the summary and the report name it.
- **Reports and summary (FR-014):** reports are written beside the output
  (with `--to sbem`, `<model stem>.report.json` beside each `<model stem>.sbem.json`, as 002's
  `Reduction.write` names them; with `--to umi`, `<output stem>.<model stem>.report.json` and
  `<output stem>.loss.json`; for translation, `<library stem>.loss.json`). The command prints a summary to stderr: models reduced and failed, counts of
  losses and approximations, report paths.
- **Parallel runs:** `-p N` runs up to N models at once in separate processes; each model is
  one reduction with at most one simulation. It is a convenience of this command, not batch
  orchestration (spec assumption, C-06).

**Rationale.** Keeping v2's names and short flags makes scenario 1.4 work unchanged; rejecting
removed options by name meets FR-013 without silently ignoring anything. Exit statuses above 2
leave click's own codes untouched.

**Alternatives considered.** *Typer.* Rejected: an extra dependency on top of click for no
gain, and no `mkdocs-click` equivalent.

## R7 — Removed v2 names, modules, commands and options

**Decision.**

- **One table.** `src/archetypal/_removed.py` holds `REMOVED: tuple[RemovedCapability, ...]`
  (data model: RemovedCapability) for every public v2 name, module, command and option.
- **Names** (`from archetypal import IDF`): `archetypal/__init__.py` defines a module
  `__getattr__` (PEP 562) that raises `RemovedInArchetypal3Error` for any name in the table.
  The error derives from `ImportError` and `AttributeError`, so `from … import …` and attribute
  access both raise it. Its message gives the name, its replacement or reason, and the
  migration guide's URL (FR-016). No alias works: nothing from v2 is carried as is (C-04).
- **Modules** (`import archetypal.idfclass`): one two-line stub module per removed v2 module
  (`dataportal`, `eplus_interface`, `idfclass`, `plot`, `reportdata`, `schedule`,
  `simple_glazing`, `tabulardata`, `template`, `umi_template`, `utils`, `zone_graph`) calls
  `raise_removed(__name__)`. A unit test checks that every module in the table has a stub and
  that each stub raises.
- **Options and commands:** `REMOVED_OPTIONS` (R6) is derived from the same table.
- **Migration guide coverage (SC-003).** `verification/v2_surface.py` runs in a separate
  environment with `archetypal==2.18.11` and writes `tests/data/v2_surface.json`: every public
  module, every public name each defines (no leading underscore, defined in that module or
  listed in `__all__`), every click command and option. The file is committed. Unit tests
  check that:
  - every entry of `v2_surface.json` is in `REMOVED` or in the v3 public interface;
  - every entry of `REMOVED` appears in the migration guide's table, with its replacement or
    reason (the guide's table is generated from `REMOVED` by a docs hook, so they cannot
    drift);
  - importing or invoking each one raises the migration error (SC-007).

**Rationale.** One table drives the errors, the guide and the coverage check, so they cannot
disagree. Stub modules are plain, typed and visible; they need no import hook.

**Alternatives considered.**

- *A `sys.meta_path` finder for removed modules.* Rejected: it changes global import state when
  archetypal is imported, against the spirit of FR-006.
- *Writing the guide's table by hand.* Rejected: it would drift from the errors.

## R8 — Errors

**Decision.** `src/archetypal/errors.py` holds one hierarchy for the whole package, extended by
002 and 003:

```text
ArchetypalError
├── InputError                 invalid input (FR-010)
│   ├── ReductionError         spec 002: NoConditionedZones, MissingResults,
│   │                          ModelResultsMismatch, UnsupportedEnergyPlusVersion
│   ├── UmiFormatError         spec 003: refused dialect, malformed JSON, broken reference
│   └── UmiValidationError     spec 003: completeness and range problems (.problems)
├── UnsupportedFeatureError    a model feature the operation cannot handle
├── LossyTranslationError      strict mode; .report holds the report of what would be lost
├── NotComparableError         spec 002
├── OptionalDependencyError    names the extra to install (FR-005, FR-010)
└── RemovedInArchetypal3Error  also ImportError and AttributeError (R7)
```

Every error takes the input at fault (a path, a zone name, an option) as a required argument
and puts it first in its message (FR-010).

**Rationale.** A script can catch any one cause, or every archetypal error at once. Requiring
the input at fault in the constructor makes FR-010 hold by construction.

## R9 — Platforms and Python versions

**Decision.**

- `requires-python = ">=3.10,<3.13"`. pip and uv refuse other versions at install with their
  own message naming the required range (FR-001, edge case).
- CI unit tier: Python 3.10, 3.11, 3.12 on Ubuntu, and 3.12 on macOS and Windows. The tutorial
  job (SC-001) runs on all nine Python × OS combinations, but only on milestone tags and weekly,
  because it installs from a clean environment.

**Rationale.** Nine combinations on every push would cost far more than they catch. Pure Python
code differs by OS mostly in paths, which the 3.12 runs on macOS and Windows cover, and
SC-001's install check still runs everywhere before each milestone.

## R10 — No side effects (FR-006, SC-006)

**Decision.**

- archetypal reads no environment variable and writes no file at import. Its loggers get a
  `NullHandler` only; only the command line configures logging, to stderr, from
  `--log-level`.
- A unit test imports archetypal and runs every command in a temporary working directory, with
  `HOME`, `XDG_*` and `TMPDIR` pointed into it, then compares the directory trees before and
  after: only the requested outputs may appear. It also checks that the root logger's handlers
  are unchanged after import.

**Rationale.** v2 created data, cache, log and image folders and read `ARCHETYPAL_*` variables;
users reported both. A test that compares trees catches any regression, wherever it comes
from.

## R11 — v2 lifecycle (FR-020, FR-021, FR-025)

**Decision.**

- **At the start:** cut `v2.x` (R2). Read the Docs keeps building v2 docs from it.
- **At M1:** a `2.18.12` patch from `v2.x` adds a docs banner and a README note inviting v2
  users to try the milestone from git (roadmap C-18) and linking the migration guide. Read the
  Docs' default version becomes `v2.x`.
- **Before v3.0.0 on PyPI:** a final v2 release announces v3 in its release notes and docs
  banner and links the guide (FR-021). The guide states the support policy: security fixes
  for 12 months after v3.0.0, or until spec 004's TABULA reader is released on PyPI, whichever
  is later; the end date is filled in when v3.0.0 is released (FR-020).
- No runtime warning is added to v2: it would change v2's behaviour in a security-only line.

## R12 — Install size and duplicates (FR-002, FR-004, FR-005, SC-002)

**Decision.**

- **Duplicate check.** A unit test resolves the default install (`uv pip compile` on the
  project, Python 3.12) and fails if it contains `eppy`, `geomeppy`, `esoreader`,
  `energy_pandas`, `pyclipper`, `pypoly2tri`, `transforms3d` or `shapely` (geomeppy's
  dependencies).
- **Count.** A `verification/install_size.py` script resolves archetypal 2.18.11 and v3 on
  Python 3.12 and reports both package counts; the milestone checklist requires v3's to be
  smaller. The count depends on epinterface's own dependencies, which UP-4 makes optional in
  the fork (Prisma, geopandas, ladybug); if the count fails, UP-4 is the fix, not archetypal.
- **Extras.** No optional extra is needed at M1: reduction and UMI translation need only the
  default install. `OptionalDependencyError` (R8) and an `_optional.require(module, extra)`
  helper exist so the first optional feature (spec 004's readers) uses them.
- **Data.** archetypal ships no data at M1. The tutorial's example model is downloaded from the
  repository at the milestone tag; it is a DOE prototype (public domain), and its source is
  stated on the tutorial page (FR-004, C-15).

## R13 — Where 001's work sits in the order of implementation

**Decision.** 001's tasks fall in two parts:

1. **Foundation**, done first, before any 002 or 003 code: generation (R1), branches (R2),
   tooling (R3), agent instructions (R4), the docs skeleton and checks (R5), errors (R8), no
   side effects (R10).
2. **Surface and migration**, done after 002's and 003's public functions exist: command line
   (R6), removed names (R7), migration guide, tutorial, install checks (R12), v2 lifecycle
   (R11).

Spec 002's tasks start from the foundation instead of repeating it.

## R14 — Dependencies on spec 003

**Decision.** The command line's UMI output and `translate` command call spec 003's public
functions. 003 has no plan yet, so 001's contract names what it needs from 003, not how 003
provides it:

- read a UMI library into SBEM archetypes, with a loss report;
- write SBEM archetypes (one per model) to one UMI library, with a loss report;
- a strict mode that raises `LossyTranslationError` instead of reporting.

003's plan names them (003 research R17, contracts/python-api.md): `read_umi(path, *,
strict, skip_invalid_templates) -> UmiImport`, `write_umi(archetypes, path, *, strict,
overwrite) -> TranslationReport` and `to_umi(...)`, raising `UmiFormatError` and
`UmiValidationError` (both `InputError`) and `LossyTranslationError`. Status 4 is returned
when the report's `losses` is not empty.
